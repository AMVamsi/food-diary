Bottleneck analysis and decisions
ML inference — 87.1%

LogMeal food recognition runs on external servers. Wall time blocked in ssl.SSLSocket.read = model is processing.

Cannot be optimised from application code. Changeable only by replacing the external API.

Storage — 8.2%

Supabase Storage PUT = 291 ms. Image upload runs after ML inference returns.

Failure is non-blocking — diary save proceeds regardless. Postgres diary queries not a bottleneck at current scale.

Python code — 4.7%

FastAPI routing, dependency injection, Pydantic validation, JSON serialisation = ~165 ms combined.

Per the course: "optimise what gives benefits, not what is easy." 4.7% yields at most 165 ms on a 3,547 ms request — not worth optimising.

Decision: no Python optimisation

Course principle applied (lecture slide 33): "Optimise YOUR code — if a library function is slow, change libraries." The bottleneck is external.

Existing high-level mitigations already in place: 30 s timeout · 429 proxying · 24 h ingredient cache · non-blocking image upload

Profiling loop: Write → Measure → Find bottleneck → Decision documented
Frontend profiling (React Native) not completed — would require Flipper connected to device during a real session.
